# Same-URL UI views and natural read-only POST coverage

## Root causes

Comparison with version 1.5.0 (commit `f5f0e92`) found an action-filter
regression: newly blocked action words were matched as arbitrary substrings.
For example, Address book matched `add` and Credit reports matched `edit`.
Safety matching now uses whole action words and punctuation-separated phrases.
CamelCase/acronym boundaries are retained, so DeleteAccount remains blocked
without rejecting CreditReports. Explicit destructive actions, forms and
disabled controls remain prohibited.

There were also longstanding coverage gaps, present in 1.5.0 as well:

- Tabs with unchanged URLs were merged into the parent URL identity.
- Non-routing `#panel` tab anchors were excluded from safe menu expansion.
- Semantic SPA links were loaded directly, skipping native click handlers and
  their naturally generated business API requests.

## Focused changes

- `app/discovery.py`: discover visible, semantic tabs with evidenced controlled
  panels. Keep their opaque UI-view identity separate from actual browser URLs.
  Initially selected panels are covered by the document, not clicked again.
  Queue inactive views rather than activating them during menu discovery.
  Validate each tab through its actual native control and require selected-state
  or revealed-panel evidence. Reject ambiguous/no-op controls. Try native
  semantic link activation before document fallback; once a click is attempted,
  never retry it or issue a fallback navigation after failure.
  Delayed native document navigation retains its actual HTTP response even when
  the requested destination redirects to another final URL; final scope and
  network-safety checks remain enforced by the existing scan pipeline.
- `app/main.py`: queue and validate UI views independently, using the existing
  browser context, deadlines, readiness, network safety, read-only policy and
  API lifecycle observer. Retain real requested/final/canonical URLs. Attribute
  naturally generated POST requests to the view activation that caused them.
  Report action-limited/unvisited views as incomplete coverage, not success.
- `app/static/app.js`, `app/static/index.html`: retain every view result, expose
  UI tab/view filtering and safe identity evidence without a layout redesign.
- `tests/test_navigation_control_safety.py`, `tests/test_ui_view_discovery.py`:
  local-browser regressions for action words, hidden templates, no-op/ambiguous
  controls, failed clicks without retries, same-URL/hash panels, native SPA
  handlers, exact-once POST receipts, approval enforcement and coverage limits.
- `tests/ui_check.py`: same-URL view rows, navigation filter and inspector evidence;
  cancel report-scroll animation before measuring pointer-drag coordinates.
- `tests/test_popup_discovery.py`: give the delayed-popup fixture execution
  headroom on contended hosts without changing its short observation window or
  coverage assertions. Application timeout behavior/defaults are unchanged.
- Release metadata: application/footer, debug base, deployment, README commands
  and health-version assertion aligned to 1.12.1.

No changes to corporate trust, certificate files, TLS verification, SSO policy,
SSRF policy or POST approval rules. No private target identifiers or browser
session state are included. POST health remains passive: only requests actually
generated by the page are observed; undiscovered endpoints are not fabricated,
replayed or automatically granted approval.

## Deployment verification

After publishing and deploying the new version, verify its actual image digest
and `/healthz` version. Enable link/UI discovery and use nonzero navigation
actions, sufficient route/depth/deadline budgets and the approved read-only POST
rules for the target. Same-URL tabs should appear as named `UI_VIEW_ACTIVATION`
rows with distinct `route_id` values and unchanged real `canonical_route` URLs.
Inspect each view's API observations and the observed/approved/executed POST
counters. A missing/expired authenticated profile or an exhausted budget must
remain an explicit coverage limitation, not claimed complete portal validation.

Private-portal behavior must be verified after deployment by its authorized
operator. Local fixtures cannot establish coverage of every proprietary UI
framework or of a portal that was not actually scanned.
